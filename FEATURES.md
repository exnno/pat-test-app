## Sheet scrollers, audited and unified (V76)

**The follow-on V75 promised.** V75 fixed the welcome modal and said plainly that other sheets might carry the same latent risk, and that a proper audit belonged on the backlog rather than being half-done in that release. This is that audit and its fix, in one change set.

**What the audit found.** All 30 sheet render sites were read. Most are genuinely fine. Three have a body whose height is set by the USER'S OWN DATA and no scroller at all: the fail-reason picker (the reason list is editable in Settings, and "Other…" plus the camera button sit below it), Multi Pick, and bulk "Change type" on the Overview — which is the worst of them, because it shows every item type in the active preset AND puts the keyboard up, so it fights the reduced cap at the same time. One was half-done: the preset switcher's list was marked in v47 but the "Edit presets" button below it never was, so it compresses instead of clipping — a different symptom of the same fault. Three more in `feedback.js` take their message text from whoever calls them, including the app's own error reporter, where long text is the normal case rather than the odd one.

**And one real defect, shipped since v33.** The first-run wizard's body hand-rolled its own scroller and omitted a single property, `min-height: 0`. A flex child will not shrink below its content height without it, so the body never shrank, never scrolled, and the shell clipped it — and because the wizard's button row IS pinned, the clipped part was Continue, Back and Skip. On the first screen a new install ever shows. It survived four dozen releases because it only bites on a short screen or with the keyboard up, and the rule it broke was written down but not enforced.

**The root cause, which mattered more than the instances.** There were three separate scroller implementations in the stylesheet — the shared class and two hand-rolled copies. A rule only helps if it is the only way to do the thing; two private copies is precisely how a sheet opts out of it by accident. V76 deletes one, reduces the other to the padding it actually needed, and adds `.sheet-pin` for the other half of the rule (the sibling below a scroller, which V75 had solved with a one-off). The harness now fails on any rule anywhere that scrolls, takes the free space and omits `min-height: 0` — including rules for sheets nobody has written yet, which is the only part of this that does not decay.

Nothing about how the app records a test changed.

## Bottom sheets and the on-screen keyboard (V75)

Every panel that slides up from the bottom of the screen — the fail reason picker, the readings sheet, bulk edit, the bug report form, first-time setup, the confirm dialogs — is `position: fixed` and anchored to the bottom of the viewport. **On iOS the keyboard does not shrink the layout viewport, only the visual one**, so a fixed element keeps its full-screen geometry and its lower part, buttons included, ends up underneath the keyboard. iOS then tries to rescue the focused field by scrolling the document, which drags the fixed overlay around, while the sheet's own scroller moves independently. Two scrollers plus a mispositioned overlay is what the sliding-about was. The fix measures `window.visualViewport` — the only thing that knows the true visible rectangle — and publishes four custom properties onto `<html>`, which the sheet CSS reads: how far the keyboard has eaten into the bottom, how much height actually exists above it, a flattened bottom padding, and a release for the wizard's height floor.

**The shape matters more than the arithmetic.** There are around 28 sheet-open sites across five files. Hooking each one would have been 28 chances to forget one — and a forgotten one reproduces the original bug in a single sheet, which is the hardest possible thing to notice. Publishing to `<html>` instead means the mechanism never has to find an open sheet, or know that sheets exist; any rule that reads the properties is fixed the moment it paints, including sheets not yet written. The cost of that shape is a new standing rule: **a sheet rule that overrides `max-height` or `min-height` opts itself out unless it uses the variable too.** Two did. `.bug-sheet` capped itself at 88vh, and `.wizard-sheet` carried both a 92vh cap **and a 72vh floor** — and the floor is the sharper trap, because a cap that is too generous merely fails to help, while a floor actively forces the sheet taller than the space above the keyboard, so it overflows off its own *top*. The title vanishes upward and it reads as a completely different fault. Both now participate. For the same reason the cap could not simply become a smaller `dvh`: `dvh` and `vh` are fractions of the *screen*, so with the keyboard up any fraction of the screen still exceeds the space that exists.

**Keyboard-down removes the properties rather than setting them to zero,** and that distinction is the whole fail-soft contract. Removing restores the `var()` fallbacks — 85dvh, the safe-area padding, the wizard's floor — which is byte-for-byte the previous release's CSS. Writing `0px` would instead pin real values over the top of the fallbacks and quietly change the no-keyboard case, which is most of the app's life. Likewise, a device with no `visualViewport` at all never has a single property written, so nothing about a sheet's ability to open, paint or be dismissed depends on any of this. Small viewport changes — browser chrome settling, tens of pixels rather than hundreds — are ignored, or sheets would twitch during ordinary scrolling.

**Focus, and a gap that had been visible in a comment for eight releases.** A bare `.focus()` on a field inside a fixed sheet is what makes iOS scroll the document to "reveal" it, and the scroll is never wanted there — the sheet is already fully visible. `focusAssetForScan()` in the scanner has carried a `preventScroll` guard, with its reasoning written beside it, since V67; the sheets never inherited it. Five call sites now route through one `focusInSheet()` helper, with a fallback to a bare focus for older WebKit, which throws on the options object rather than ignoring it — failing back to the old behaviour beats failing to focus at all, because a field that never takes focus is a dead form. Deliberately **not** converted: the notes field on the entry screen, which is not in a sheet and has no fixed overlay to drag, and where suppressing the reveal-scroll could hide it behind the keyboard instead.

**Not done, and this is a standing prohibition rather than a scoping decision:** locking body scroll while a sheet is open. It is the obvious fourth part, and it is the same family of trick as the `100dvh + overflow:hidden` layout this app banned after it trapped content behind the keyboard in v12 and had to be rolled back in v12.1. The other parts solve it without touching the page. A harness assertion now guards the shipped source against its return.

**The welcome modal, folded in.** V74's What's New panel could not be dismissed on a phone: its Continue button was clipped off the bottom with nothing to scroll. Same family, different cause. The sheet shell has been capped with `overflow: hidden` since V57, and the rule there is that the one child which can grow long must be marked as the scroller — this list never was, because when it was written in V11 nothing could grow, and the comment above it said so. Five long bullets in V74 went straight past the cap. The list is now a designated scroller, the button is pinned below it, and short copy is discipline rather than the only thing between a user and the way out. Other sheets may carry the same latent risk; that is a proper audit and is on the backlog rather than half-done here.

**Harness:** 13 new groups (11a–11m, 57 assertions) and 8 mutations (M89–M96). Two stub-layer changes were needed and one is worth recording: the fake element's `style` was a plain object, which literally cannot express the difference between "property removed" and "property set to `0px`" — the exact distinction this release turns on — so it became a real, if small, `CSSStyleDeclaration`. `visualViewport` is **absent by default** in the harness, which makes the no-support path the default state a forgetful test lands in. One assertion failed on its first run and was a harness defect, not an app bug: it searched for `100dvh` to prove the banned layout had not returned and matched the three comments that document the ban. It strips comments now, and asserts the stripper left live CSS behind so it cannot silently become a check against an empty string. What none of it proves, and the file says so plainly: there is no layout engine here, so nothing demonstrates that a sheet *visually* clears the keyboard. That proves itself on a phone and nowhere else.

## Barcode scanner, second contact: the two timing bugs (V74)

Two defects found on real jobs with real hardware, both of the invisible kind, and both ported by hand from findings written up on PATGo Scan (separate codebase, no shared code — the causes were described and located afresh here). **The wrong-number one first, because it is the only fault in the scanner with a data-correctness consequence.** When a burst was dropped part-way through — an unreadable key arriving mid-barcode, a stray modifier, a Bluetooth hiccup — the scanner carried on typing, and the *remainder* formed a brand-new burst of its own. Short, fast, above the three-character minimum, and entirely plausible as an asset number: `PAT-004821` interrupted after five characters delivered `4821` into the asset box and onto a certificate, with nothing on screen to suggest anything had happened. Discarding the burst in progress was never enough; the app now refuses to collect anything at all until the keyboard has been silent for a full end-of-burst window, and that window **slides** — every character inside it pushes it out again, so a scanner that keeps typing keeps being ignored until it genuinely stops. Only the unreadable-key path arms it: the other place a burst is discarded is the ordinary "not a scan target" bail, which fires many times a second during normal typing, and arming there would blank a genuine scan for a fifth of a second after every field the engineer leaves — a guard against a case that cannot happen, since nothing was collected and there is no tail to protect against.

**The second defect is the more instructive.** A second HID scanner was measured emitting characters 100–115ms apart, and PATGo rejected it on *every* speed setting — the trigger simply did nothing, which is the same silent failure V67 existed to remove. The cause was that there were **two independent ceilings and only one of them was configurable.** The gap preset judged whether a burst was fast enough to be a scan; a separate flat constant, `SCAN_END_MS = 120`, decided where one burst ended and the next began, and any gap above *it* wiped the buffer and started over. So raising the preset alone does not help — it makes things worse. Past 120ms the burst stops failing as "too slow" and starts failing as "too short", because the buffer restarts on every single character and a one-character burst is what reaches the length check. A flat constant silently capped how far any preset could ever be relaxed, and nothing in the code said so. The boundary is now **derived** — the active gap limit plus a 70ms pad, floored at 120 — so widening a preset widens the boundary with it, permanently and without a second edit. The invariant, stated plainly and pinned by a test across every preset: *the end-of-burst window must always exceed the gap limit.* Presets moved 40/60/90 → **60/90/150**, giving windows of 130/160/220.

**Why the preset values moved and not `SCAN_SPEED_DEFAULT`.** Changing the default would have fixed nobody. `saveSettings()` writes `SCAN_SPEED_KEY` unconditionally on every settings save, so every phone that has ever opened Settings already holds an explicit `'normal'` and never consults the default again. Moving the *numbers behind the names* is what reaches an existing fleet without anyone touching a setting — and the same reasoning applies to any future tuning value that looks changeable via its default. Accepted knowingly: `'relaxed'` at 150ms genuinely overlaps fast typing. Two things keep the exposure small — the three-character minimum, and the focus rule in `_scanTarget()`, which declines outright while any *other* text field is focused, so Location and Notes cannot be misread. What remains is fast typing directly into the asset box, which would write back the same digits it was given; the one real side effect is that it also sets `scanFilledAsset` and suppresses the next auto-increment. The settings page copy now says what Relaxed costs and suggests returning to Normal once a stubborn scanner is working. **Harness:** 11 new groups (08y–08y5, 08z–08z4) and 6 mutations (M83–M88); four existing groups retuned for the new numbers, and three older mutation anchors re-pointed. One new group had to be rewritten mid-release — the first version of the silence-timer test waited 300ms of real time and passed against a build with the timer hard-coded back to 120, because an early timer still commits a burst that was going to be accepted anyway. It now inspects the delay handed to `setTimeout`. That is the "right result via the wrong mechanism" shape, caught by its own mutation exactly as intended.

## Apostrophes: repairing what the fix left behind (V69)

V68.1 stopped the app mangling apostrophes; **it did not repair anything already
stored.** `titleCase()` runs at SAVE time only, so every location and item type
written under V68 or earlier kept its `Bob'S Office` form, kept printing that way
on certificates and CSV exports, and — the part that made it more than cosmetic —
kept being offered back by the location autocomplete, so tapping a suggestion on
a *fixed* build wrote the old bad string into a brand-new item. The bug outlived
its own fix through the suggestion list. V69 is a one-time rewrite of stored data,
the first this app has done.

**The repair is `titleCase()`'s inverse and the only code here that lowercases a
letter the user might have typed on purpose**, which makes its two guards the
whole design rather than details. The word before the apostrophe must not be
all-caps, so `BOB'S OFFICE` — deliberate shouting — survives untouched; blindly
lowercasing would have introduced a *worse* defect than the one being fixed, on a
string the engineer typed intentionally. And the suffix must be a single letter,
so `O'Brien`, `Sant'Angelo` and `Dell'Arte` are never touched. All three
apostrophe characters are handled and the typed one is preserved, never
normalised. Scope is item locations, item types and preset entries; client and
site names never passed through `titleCase()` and were never mangled, and Smart
Quick Pick lowercases its keys before storage so its buckets were always correct.

**A file backup could not be taken before the rewrite, and that constraint is
permanent.** `downloadBackup()` fires a synthetic anchor click — it needs a user
gesture and on iOS opens the share sheet, so nothing silent is possible at boot.
Instead the repair records only the strings it changed as a diff, surfaced as an
**Undo the correction** button on the Backup page, and trips the existing 7-day
backup reminder so the user is pushed toward a real off-device copy at a moment
when a gesture is available.

**The trap that nearly made the whole release a no-op:** `serialiseSessions()`
reuses a session's cached encoding when the items array reference and a signature
covering item *count* are unchanged. The repair edits strings inside existing item
objects, so all three checks passed and the repaired data would have been written
back from the stale encoding — appearing to work, then reverting on the next
reload. It only bites NON-ACTIVE sessions, because the active one always
re-encodes fresh, which is exactly why the first test of it passed against broken
code. Old jobs are the real case, and old jobs are where the mangled data lives.

Also fixed, defect **D4**: `handleDelegatedClick` called each action bare, so a
throw from a view renderer escaped. It never showed as a blank screen —
`render()` assigns `#app.innerHTML` in one statement at the end — but the action
had already changed `state.view`, so state and screen disagreed and the next tap
ran the wrong screen's actions. Now caught and recovered to the Sessions list.
No new files, no `backupVersion` bump (stays 5). Two new storage keys, both
additive. Validated at 486 assertions and 51 mutations, 0 survived.

## Three defects, a removed button and a navigable stylesheet (V68)

A cleanup release with no new capability, and the interesting part is what the harness did to it. **`titleCase()` had been capitalising the letter after an apostrophe since the function was written** — `/\b\w/g`, and an apostrophe is a word boundary, so "Bob's Office" was stored as "Bob'S Office". It was not a display bug: `normaliseLocation()` runs at save time, so the mangled string reached certificates and CSV exports and had been doing so for every customer with a possessive in a place name. The fix had to be narrower than it first appears — "ignore apostrophes" would break O'Brien, which is a real name people have — so only a **single** letter following an apostrophe is left alone, and both directions are asserted plus mutated (M36 reverts it, M37 over-corrects it). **The boot integrity guard could throw instead of returning false**, which is the failure it exists to prevent arriving through the front door: if `config.js` fails to parse, `state.js` throws while evaluating `let state = {…}`, leaving `state` in the temporal dead zone, and `typeof state` on a declared-but-uninitialised binding throws ReferenceError rather than returning `'undefined'`. A comment in `boot.js` asserted the opposite, which is why it survived review — `typeof` is safe on an *undeclared* identifier, and the distinction is easy to read past. The call site is now wrapped and a throw counts as a failed check. Writing the test for it surfaced a second, subtler point: **two "Update needed" screens exist** — the guard's and the v61.2 `load()` net's — and they share a title, a Reload button and a mailto link, so a mutation that made a throw count as a *passed* check still produced a correct-looking recovery screen and survived. Only the explanatory sentence differs, and the assertion now depends on that wording to prove boot stopped at the guard rather than being rescued downstream. **Captured error text was reaching the support email verbatim**, the one field in the bug report the privacy rule could not cover by construction: everything else is a count, a flag or an enum, but an error message is whatever the browser happened to say, and one that interpolates a value carries a client name off the phone. It is now scrubbed against every customer string in memory at report-build time. The first version of that scrub **failed open** — a term list that came back empty meant "nothing to redact", so a throw while gathering terms turned the whole thing into a passthrough on exactly the case it was written for. The harness caught it on the first run; it now fails closed and withholds the message rather than guessing. Also removed: **the V67 ⌨ escape-hatch button**, which could not work in the case people actually hit. iOS hides the on-screen keyboard system-wide whenever a hardware keyboard is paired and no web API overrides that, so the button was only ever useful when the scanner was off or out of range — a case the "Scanner paired" setting already covers properly, by removing the suppression at its source. A control that fails in its main use teaches the engineer the app is broken rather than the platform is, so it is gone along with its state flag, and the settings page now names the two things that do work: the scanner's own double-click-trigger shortcut, and turning the paired switch off. Finally, `styles.css` gained a **section index** — 49 banner comments and a header block, proved comment-only by stripping the banners back out and byte-comparing against the original. The file is ordered by release rather than by screen and was not reordered to match: CSS is order-sensitive, several rules depend on being overridden later, and a navigable stylesheet is not worth a cascade bug.

## Barcode scanner, first contact with a real device (V67)

The V65 scanner support was written against spec sheets and never tested against hardware. The first physical unit (a NETUM C750, Bluetooth HID, iOS) did not work at all — and the reason it took a release to diagnose is the point of this entry: **it failed silently.** Three separate-sounding symptoms reported from the field ("I have to tap the box first", "a re-scan appends instead of replacing", "after PASS the next scan goes nowhere") were one cause. Every burst was being rejected, so the app did nothing, and "did nothing" is indistinguishable from "no scanner paired". Raw hardware-keyboard passthrough was all the engineer ever saw. **The design principle that came out of it: a safety mechanism that can reject must be able to say why.** `_scanVerdict()` now returns the character count, the slowest gap measured and a reason string instead of a boolean, and the settings test page logs rejected bursts alongside accepted ones. A scanner that is not connected and a scanner that merely needs a setting changed no longer look the same. Three actual defects were fixed. **Modifier keys were destroying the buffer**: a scanner sending an uppercase character emits its own Shift keydown, and V65 treated any non-single-character key as "burst over" — so a barcode with capitals part-way through killed its own scan. True modifiers now pass through without ending the burst, but everything else still drops it, and the asymmetry is deliberate: skipping a key that *did* produce a character would leave it out of the buffer and overwrite the asset box with a plausible-looking **short** number, which is far worse than no scan at all. **The speed threshold was too tight.** 40ms was a guess; the default is now 60ms and the engineer can choose strict/normal/relaxed on the settings page, because a device in someone's hand should not need a release to debug. **A CR+LF scanner sent two Enters** and only one commit path armed the swallow window, so the second escaped — realistic rather than theoretical, since the C750 has a one-barcode shortcut for exactly that terminator. Added alongside: **paired mode**, an opt-in switch (`SCANNER_PAIRED_KEY`, ordinary `=== '1'` polarity sitting one line below the app's only `!== '0'` read — the neighbour-copying hazard, harness-asserted both ways). With it on, the entry screen puts the cursor in the asset box on render *and* after every log, with `inputmode="none"` keeping the on-screen keyboard down; the focus call `select()`s as well, so even a burst that somehow escapes detection replaces the pre-filled number instead of appending to it. It is gated separately from the master switch because scanning is on for everyone and a self-focusing field is only ever right when a hardware keyboard is attached. A ⌨ button beside the box lifts the suppression for one item — and the settings copy is explicit that it **cannot** raise the keyboard while a scanner is connected, because iOS hides the software keyboard system-wide whenever a hardware keyboard is paired and no web API overrides that; the answer there is the scanner's own double-click-the-trigger shortcut. Two new localStorage keys, both additive and missing-field-tolerant, **no `backupVersion` bump** (stays 5). **The harness had no keydown coverage whatsoever before this release** — nothing would have caught the V65 failure — so V67 added 24 groups driving real bursts through a controllable clock, plus 11 mutations. Two harness defects surfaced on the first run and both were the documented shapes: fixture apps never cleared `welcomeSeen`/`onboardedV33Seen`, so `_scanTarget()` declined every burst and thirteen groups went red against correct code; and the "too slow" test used a 200ms gap, which exceeds the burst window and is therefore treated as the start of a *new* burst, so it died on length and never reached the speed test. Both read as app bugs and were neither.

## Multiple test instruments, and jobs that remember which one did them (V66)

Settings → User Settings now holds a **list** of PAT testers (up to five, decision 6A) instead of a single set of boxes, each with its own make, model, calibration date, certificate number and due date, one marked **In use**. **The feature is real but the reason for building it was a defect.** Before V66 those five values were flat globals read at PDF render time, and nothing was recorded on the session — so reprinting a March certificate after a June recalibration printed **June's** calibration dates against **March's** results, on a document the engineer certifies, and getting worse the longer the app was used. Sessions are now stamped with `instrumentId` at creation and the certificate resolves through that. **The architectural decision that kept this release safe: the five flat fields were not removed, they became a live mirror of the active instrument.** Ripping them out would have meant rewriting storage's legacy keys, both backup paths, the Setup export/import and the first-run wizard simultaneously, in a release that already moves the data model; keeping them as a mirror meant every one of those paths kept working untouched and converged on the list through one of three clearly-named sync functions. The standing rule written into the code: **anything that writes a flat field directly must call `adoptMirrorIntoInstruments()` afterwards**, or the write is silently discarded on the next sync. **Resolution is one helper with three tiers** — stamped instrument, then the frozen snapshot, then the active instrument — called by the PDF, the CSV and the UI alike, so "which instrument does this job show" is decided in exactly one place; tier three is what makes every pre-V66 job print exactly as it did. **Deleting an instrument freezes a copy onto the jobs that used it** (`session.instrumentSnapshot`) before removing it, because the obvious alternative — letting those jobs fall back to whatever is active today — is precisely the defect being fixed, and the other alternative, blocking deletion, would trap the user with every tester they have ever owned. Calibration warnings now cover **every** saved instrument rather than only the one in use (decision 5B), as **one** banner naming the worst offender with "+N more" appended, because two stacked banners on the Sessions screen would be worse than the problem. A small long-standing annoyance went with it: **a calibration date could never be emptied once entered** — the save path handled empty strings correctly all along, but `<input type="date">` offers no way to *produce* one, so a date typed while exploring was permanent; each date now carries a **Clear** link, written as a targeted DOM write rather than a re-render so it cannot discard the editor's other unsaved fields. One new file (`instruments.js`, **24** first-party scripts now), two new localStorage keys, two additive session fields, **no `backupVersion` bump** (stays 5 — the session codec passes unlisted fields through and both restore paths are missing-field-tolerant). Validated by the full sweep plus a **177-assertion** stubbed-DOM harness driving the shipped `load()`, `save()`, `buildBackup()`, `applySetupBundle()` and the real codec, then **mutation-tested 25 ways**. **The mutation run again earned its keep, four times over:** the "deleted instruments must not resurrect" assertion turned out to be satisfied by the mirror blanking rather than by the check it was aimed at; the report path was not exercised *at all* (it cannot run headlessly without jsPDF, and is now source-guarded against reading `state.*` again); and neither the first-run wizard's write into the list nor the User Settings save were covered. It also surfaced a genuine code smell rather than a test gap — a `findInstrument` guard around dropping a stale snapshot that could be deleted with every assertion still green, because it protected nothing reachable; the code was simplified rather than the test strengthened.

## Barcode scanner, HID path (V65)

the app now works with a Bluetooth barcode scanner: the sort that pairs with a phone as a keyboard, sold as a "wedge" or HID scanner. Scan an asset label on the test screen and the number goes straight into the asset box; scan on the Sessions list and it searches for that asset, which reaches the V61 cross-session history card for free. **The HID path was chosen over a phone-camera scanner deliberately** — it is a cheap way to find out whether barcode workflows matter to the wider audience before committing to the much larger camera build (permissions, a detection library, and iOS PWA camera quirks with their own history of not working first try). If testers with existing scanners start using it, that is real evidence for the camera build; if nobody cares, very little was spent finding out. **The roadmap framing turned out to be slightly wrong, and the code corrected it:** the plan said "catch the trailing Enter and commit the item," but the asset field is a plain input with no keydown handler, so a scan only landed if the field had been tapped first — which pops the iOS keyboard over the Quick Pick grid. Removing that tap, not the Enter, is the actual prize. Auto-logging on Enter was rejected at spec time for a related reason: item type is mandatory and resets after every log, so a scan would have logged sometimes and silently done nothing at others, and behaviour that depends on invisible state is worse than behaviour that never fires. **The timing test is the whole safety mechanism.** A wedge scanner is indistinguishable from a keyboard by design, so the only measurable difference is speed: a scanner emits characters ~5–20ms apart, a fast typist ~80–150ms. Every gap in a burst must fall under 40ms and the burst must reach three characters, so one slow gap means a human paused and the buffer is discarded. Key auto-repeat is excluded explicitly, being the one non-scanner source of machine-speed keystrokes. **Character keys are never `preventDefault`ed — only the terminator**, which is what makes it impossible for the feature to interfere with normal typing: at the moment each character arrives we cannot yet know whether the burst will prove to be a scan, so characters are allowed to land wherever they were going *and* buffered in parallel, and only on the terminator (or a silence timeout, for scanners configured with no suffix) is the burst judged — at which point the target field is overwritten wholesale, cleaning up whatever the characters did on the way past. If it was not a scan, nothing happened at all. Enter and Tab are both accepted as terminators. **One genuine interaction was found in review and fixed:** `nextAssetNo()` increments the last item's trailing digits, so after scanning `PAT-004821` the next box would pre-fill `PAT-004822` — arithmetic on someone else's label, which looks authoritative and is almost certainly not on any appliance. Harmless if every item is scanned, but a trap when scanning is mixed with hand-logging. So a logged item whose number came off a barcode leaves the next box **empty**, with a "Scan or type" placeholder; a hand-typed log still increments exactly as before, and the counter returns the moment one is typed by hand. The flag is scoped to the session id, so switching jobs restores the counter. There is deliberately no hard stop — an empty box still logs, falling back to the counter as it always has. A duplicate asset number warns at **scan** time rather than at save, because that is when the engineer is still stood at the appliance. A new **Barcode Scanner** page under Testing Setup carries the off switch and a **live test box** showing the raw text and character count, which is the answer to the discoverability problem a scanner with no on-screen control creates. The flag is the only one in the app that **defaults ON** and is read `!== '0'` rather than `=== '1'`: with no scanner paired the feature is entirely inert, so there is nothing to opt in to. One new file (`scanner.js`, 23 first-party scripts now), one new localStorage key, **no `backupVersion` bump** (stays 5 — the flag is additive and missing-field-tolerant). Validated by the full sweep plus an **85-assertion** stubbed-DOM harness driving real keystroke bursts through a controllable clock, mutation-tested six ways. **The mutation run earned its place twice over**: removing the speed test initially passed the harness, exposing that the "human typing" assertion used a 130ms gap — which exceeds the burst window, so it died on length and never reached the speed test at all; and the storage/backup assertions inlined the flag logic instead of calling the shipped `load()` and restore path, so mutating those files changed nothing. Both holes were closed and all six mutations then failed as they should.

## Photos on the certificate (V64)

the photos taken on a job can now be printed on the report. Switch **Photos** on under Settings → Report settings → What to include and the app adds photographic evidence pages to the end of the certificate, grouped under the asset each photo belongs to, with the asset number, description, location and the fail reason printed above the row. There's also a **Photos** chip in the report preview's quick-adjust row, so a single report can carry them without changing the saved setting. **It defaults OFF, deliberately** — the second flag in the app to do so, alongside V61's testing time, and for the same reason: anyone who has been taking photos since V62 has a certificate they are already sending to clients, and quietly adding four pages of photographs to it is not a change to make on their behalf. It is read with `=== true` rather than the `!== false` its neighbours use, so a settings blob, backup or setup bundle written before V64 backfills to off and every existing certificate stays byte-identical. **The structural problem, and the shape of the answer:** photos live in IndexedDB, which is async, while `buildReportDoc` is synchronous and has three call sites — two of them (the preview's in-place rebuild and the return from Edit report settings) synchronous themselves. Making the builder async would have pushed a database wait onto the render path, which is precisely what V62 established must never happen. Instead the photos are read and re-encoded **once, up front**, in the already-async `produceReport`, and handed to the builder as a plain second argument of ready-made data URLs; rebuilds reuse a session-keyed cache and cost nothing, and the cache is ignored outright if it holds a different job. **Sizing is the thing that decides whether this works in the field.** Photos are stored at 1280px because the on-screen strip wants the detail, but a printed slot is about 165pt wide — three across a page — so anything past ~500px is resolution nobody will ever see, while twenty photos embedded as stored is a ~5MB PDF and an iOS share sheet that struggles. Each photo is therefore re-encoded at build time, and the size is chosen from **how many the job has**: up to 24 photos at 640px, up to 60 at 512px, beyond that 400px. **The ladder exists so a big job shrinks rather than drops** — a fixed size plus a hard cap silently loses evidence, which is the one thing a photo appendix must not do; a fifty-fail job just gets smaller pictures, and even the bottom rung prints at over 170dpi. A ceiling still has to exist somewhere, because past it the PDF stops being something a phone can send and a certificate that cannot be sent has failed at its only job: at **150 photos** the report stops, and says so **loudly** — a boxed notice on the *first* appendix page stating exactly how many are shown and how many are not (not buried on page fifty where nobody would reach it), repeated at the end, plus a toast when the report is produced. **One existing bug was fixed because it had to be:** the footer pass ran *before* the declaration block, capturing the page count too early, so a declaration pushed onto a fresh page got no footer at all and every other page read "of N" on an N+1 page document. Appending photo pages after it would have made that wrong on every photo report, so the pass now runs last, once the document is complete — existing output changes only in the case that was already wrong. Everything fails soft, as the V62 photo layer does throughout: no IndexedDB, an unreadable photo, or a throw inside the appendix means the certificate builds without it. No new files (still 22 first-party scripts), no new localStorage keys, **no `backupVersion` bump** (stays 5 — `showPhotos` rides the existing report-settings blob additively). Validated by the full sweep: syntax check on all 22 JS files, duplicate-declaration scan, load-order verification, and a **77-assertion** flow-driven stubbed-DOM smoke harness that builds real documents against a recording fake jsPDF and asserts on what was actually drawn — the encode tier chosen for each job size, the ceiling, groups in register order, orphaned photos skipped, aspect-fitted images, the notice landing on the first appendix page, and one correctly-numbered footer per page. ## Welcome-key decoupling (V63)

a pure structural release with no user-visible feature, fixing the fault that caused the V61 white screen. Until now, which release's "what's new" modal was current lived in the codebase as a version-NAMED identifier (`V62_WELCOME_KEY`, `state.v62WelcomeSeen`) written into **six** files that all had to roll in lockstep every release: `config.js` defined the key, `storage.js` read it inside `load()`, `state.js` held its flag, `dispatch.js` passed it to the dismiss helper, `boot.js` guarded it, and `render-core.js` gated the modal on it. Land one of them late — a file not committed, or one still being served from a stale service-worker cache — and `storage.js` referenced an identifier `config.js` no longer declared. A bare undeclared identifier throws a `ReferenceError`, it threw *inside* `load()`, and nothing caught it: the app failed to open at all. **The V61.2 boot guard did not fix this**, it only moved the coupling from five files to six — a stale `boot.js` checks the *previous* release's name, passes happily, and `load()` throws anyway. The fix separates the two things that were conflated: the identifier **names** are now fixed forever (`WELCOME_KEY`, `state.welcomeSeen`) and only a string **value** changes between releases, and a wrong value cannot throw. That value is `WELCOME_VERSION` in `config.js`, deliberately **not** derived from `APP_VERSION`, because most releases bump the version without shipping a welcome (hotfixes, structural releases like this one) — deriving it would re-show the last modal to everyone who had already dismissed it, every release. Rolling a welcome is now a one-line edit in one file. The `storage.js` read sits behind a `typeof` guard whose fallback is deliberately **suppress the modal**, not show it: if the key were missing the app also could not *persist* a dismissal, so showing it would produce a modal returning on every launch — an undismissable modal is a trap, a missed "what's new" is a non-event. `WELCOME_VERSION` stays at `V62` here, so the key remains `pat:v62welcome` and nobody who dismissed the V62 modal sees it again, while anyone who has not opened since V62 still gets it. No new files, no new storage keys, **no `backupVersion` bump** (stays 5 — the welcome flag was never in the backup at all). Validated by the full sweep: syntax check on all 22 JS files, duplicate-declaration scan, load-order verification, and a flow-driven **30-assertion** stubbed-DOM smoke harness that drives the real path (load → render → dismiss → reopen) rather than testing functions in isolation. Mutation-tested by reinstating the v62-era coupling, which fails 8 assertions; and the V61 white screen itself was **reproduced directly** — v62-era code with a config one release behind throws `ReferenceError: V62_WELCOME_KEY is not defined` inside `load()`, while V63 under the identical condition starts normally.

## Photo evidence on fails (V62)

the app's first use of any persistence mechanism other than localStorage, and the largest architectural change since the V21 refactor. Tap **FAIL** and the reasons sheet now carries an **Add photo** button: up to three photos per item, of the damage, the plug, the rating label, whatever the evidence is. Failed items in the Overview show a 📷 chip with a count; tapping it opens a strip to view, add or delete. **Fails only, deliberately** — roughly a 5% attach rate instead of 100%, which keeps logging a pass exactly as fast as it has always been and keeps the storage footprint sane; photographing a rating plate on a *pass* was considered and rejected as a hypothetical habit that would cost both. **Why IndexedDB, not localStorage:** localStorage is a ~5 MB synchronous string store, one 1280px JPEG is ~200 KB, and base64 inflates that by a third — three photos on twenty fails would exhaust the budget the sessions blob lives in and take the sessions blob down with it. Photos are stored as native Blobs (1280px longest edge, JPEG q0.7) in a new `photos.js` holding **every** line of IndexedDB code in the app, so the async surface is one contained boundary. **The synchronous-render problem, and the shape of the answer:** `render()` cannot await a database but the Overview must draw a photo count, so the store keeps an in-memory count index in `state`, rebuilt once at boot and updated on every write — a derived mirror that is never saved, never backed up and never validated on restore, because the object store is the source of truth and persisting the mirror would let it drift. **Photos are not in your backup, and the app says so three times** — welcome modal, Backup page, and again on restore if the backup was taken on a device that had them. Embedding them would inflate a typical backup from tens of KB to tens of MB and risk the write failing on a phone, turning a photo problem into total data loss; instead there's a separate **Export photos** file. That file needs no linking metadata at all, because photo records key off `item.id` and item ids already ride inside every backup — restore a backup, import the photo file, and they re-link themselves. **Four removal paths carry the cascade** (single item, bulk delete, delete job, prune old jobs), every one sweeping *before* the splice or filter on the same ordering rule V59's stats archive follows, because afterwards the ids are gone and the photos are orphaned invisibly and unboundedly. Changing a fail to a pass gives up its photos behind a confirm that names the count and says plainly they can't be recovered — the realistic route there is correcting a mis-tap, and someone who mis-tapped needs to know what else the undo takes with it. **Failure posture: everything fails soft.** No IndexedDB, a blocked open or a throw means the photo UI hides itself and logging continues exactly as before; nothing in the photo layer may break the fail flow. One new file (`photos.js`, 22 first-party scripts), no new localStorage keys, **no `backupVersion` bump** (stays 5 — `photoCount` on the backup is informational and missing-field-tolerant). Validated by the full sweep: syntax check on all 22 JS files, duplicate-declaration scan, load-order verification, and a **97-assertion** stubbed-DOM smoke harness with a fake IndexedDB — which caught a real bug before release, where the transaction helper could not distinguish "the transaction failed" from "this batch issued several requests and has no single result", so every multi-delete silently skipped its index update and left stale counts on screen until restart. Mutation-tested three ways (removing the per-item cap, letting staged photos attach to a pass, moving the cascade after the splice), each confirmed to fail the harness before the code was restored. ## Lifetime stats counter (V59)

a running tally at the bottom of the Settings screen: how many items you've tested, how many failed and the percentage, and your most common item type. The design problem worth explaining is **pruning**. A counter computed live from the sessions currently on the phone would *fall* every time you cleared out old jobs — you'd tidy up and watch your lifetime total shrink, which reads as broken rather than fun. The obvious alternative, incrementing a stored counter each time an item is logged, is worse: it needs hooks in item save, item delete, bulk delete and CSV import, plus adjustment logic when a pass is edited into a fail, and double-counting is its failure mode. V59 uses a third shape — an **archive bucket**. The figure shown is *live* (counted from current sessions, never stored, so it can't drift from the real data) plus *archived* (a small persisted bucket). At the two — and only two — points where a session leaves the app for good, `deleteSession` and `pruneOldSessions`, that session's tallies are folded into the bucket **before** it goes. There are exactly four places the session list is reassigned (load, restore, prune, delete), so those two hooks cover every removal path with none unaccounted for. The result: clearing out old jobs no longer costs you the numbers, editing an item can't double-count, and CSV-imported sessions need no special handling because they simply appear in the live half. **Deliberate exclusions:** item-level deletes are *not* archived (that's correcting a mis-entry, not history leaving, and archiving it would let a typo permanently inflate the total), the demo/example session is excluded from both halves, and the bucket is **not** part of the Export Setup bundle — Export Setup is config-only and these are derived from job data. **Backup behaviour:** the bucket rides in the JSON backup, and restore puts it back through the same validator used on load, so restoring returns the counter to exactly what it was when the backup was taken rather than desyncing; a pre-V59 backup has no such key and correctly restores an empty bucket. Additive and missing-field-tolerant, so **no `backupVersion` bump** (stays 5). One honest limitation, stated in the app's own changelog: the counter starts from the sessions on the device at upgrade time — anything pruned *before* V59 is unrecoverable — so it becomes a true running total from this release onward. Validated by the full sweep: syntax check on all 21 JS files, duplicate-declaration scan, load-order verification of all nine new symbols, a 102-assertion stubbed-DOM smoke harness (live counting, the delete and prune hooks holding the total, demo-session exclusion in both halves, item-deletes correctly *not* archived, validator hardening against negative/fractional/NaN/Infinity/array/string input and a 200-entry type map, corrupt-storage recovery, save-through-validator, escaping, tie-break stability and zero/100% edge cases), and a 42-assertion lifecycle harness walking the real scenario end to end — log work, back up, prune everything, reload the app, restore — asserting the total never moves at any step and that restoring cannot double-count.

When it's **on**, tapping PASS opens a short bottom sheet: a class selector at the top decides which boxes show (Class II has no earth continuity; Class III is insulation only), and the boxes are pre-filled with typical pass values (`<0.1`Ω, `≥19.99`MΩ, `<5`mA) so it's still effectively a tap-to-confirm. On a FAIL, the chosen fail reason drives which single reading box appears (its tag is set on the Quick Pick Fail page; defaults ship sensibly, custom reasons default to visual-only). Readings can be added to the CSV export via four new default-hidden columns (Settings → CSV Columns). **Data-model note:** readings are stored as an additive per-item object and ride through backup/restore wholesale with a defensive validator — **no `backupVersion` bump** (stays 5), because old and new backups remain mutually compatible. (Readings reached the PDF certificate in V54.) Validated by the full sweep (syntax check, duplicate-declaration scan, load-order check, and a stubbed-DOM smoke harness exercising the pass/fail/edit/off-path/CSV/backup paths).
