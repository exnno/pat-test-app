# PATGo PWA

A fast, offline-first portable appliance testing app (formerly "PAT Test"; renamed PATGo in V48, with the last internal code references swept in V60). Records pass/fail decisions on-site, with full offline support, autocomplete from session history, sticky locations, asset prefixing, Quick Pick and Smart Quick Pick item buttons, Multi Pick sequences, flexible clients & sites, search, filters, bulk edit, cross-session asset history, per-job testing time, JSON backup/restore, dark mode, CSV export/import, and branded PDF report generation.

**Live:** <https://exnno.github.io/pat-test-app/>
**Current version:** V62 · cache `pat-v62`

## Key features

- **Photo evidence on fails (V62)** — the app's first use of any persistence mechanism other than localStorage, and the largest architectural change since the V21 refactor. Tap **FAIL** and the reasons sheet now carries an **Add photo** button: up to three photos per item, of the damage, the plug, the rating label, whatever the evidence is. Failed items in the Overview show a 📷 chip with a count; tapping it opens a strip to view, add or delete. **Fails only, deliberately** — roughly a 5% attach rate instead of 100%, which keeps logging a pass exactly as fast as it has always been and keeps the storage footprint sane; photographing a rating plate on a *pass* was considered and rejected as a hypothetical habit that would cost both. **Why IndexedDB, not localStorage:** localStorage is a ~5 MB synchronous string store, one 1280px JPEG is ~200 KB, and base64 inflates that by a third — three photos on twenty fails would exhaust the budget the sessions blob lives in and take the sessions blob down with it. Photos are stored as native Blobs (1280px longest edge, JPEG q0.7) in a new `photos.js` holding **every** line of IndexedDB code in the app, so the async surface is one contained boundary. **The synchronous-render problem, and the shape of the answer:** `render()` cannot await a database but the Overview must draw a photo count, so the store keeps an in-memory count index in `state`, rebuilt once at boot and updated on every write — a derived mirror that is never saved, never backed up and never validated on restore, because the object store is the source of truth and persisting the mirror would let it drift. **Photos are not in your backup, and the app says so three times** — welcome modal, Backup page, and again on restore if the backup was taken on a device that had them. Embedding them would inflate a typical backup from tens of KB to tens of MB and risk the write failing on a phone, turning a photo problem into total data loss; instead there's a separate **Export photos** file. That file needs no linking metadata at all, because photo records key off `item.id` and item ids already ride inside every backup — restore a backup, import the photo file, and they re-link themselves. **Four removal paths carry the cascade** (single item, bulk delete, delete job, prune old jobs), every one sweeping *before* the splice or filter on the same ordering rule V59's stats archive follows, because afterwards the ids are gone and the photos are orphaned invisibly and unboundedly. Changing a fail to a pass gives up its photos behind a confirm that names the count and says plainly they can't be recovered — the realistic route there is correcting a mis-tap, and someone who mis-tapped needs to know what else the undo takes with it. **Failure posture: everything fails soft.** No IndexedDB, a blocked open or a throw means the photo UI hides itself and logging continues exactly as before; nothing in the photo layer may break the fail flow. One new file (`photos.js`, 22 first-party scripts), no new localStorage keys, **no `backupVersion` bump** (stays 5 — `photoCount` on the backup is informational and missing-field-tolerant). Validated by the full sweep: syntax check on all 22 JS files, duplicate-declaration scan, load-order verification, and a **97-assertion** stubbed-DOM smoke harness with a fake IndexedDB — which caught a real bug before release, where the transaction helper could not distinguish "the transaction failed" from "this batch issued several requests and has no single result", so every multi-delete silently skipped its index update and left stale counts on screen until restart. Mutation-tested three ways (removing the per-item cap, letting staged photos attach to a pass, moving the cascade after the splice), each confirmed to fail the harness before the code was restored. The harness also boots **deliberately broken builds** — a stale `config.js`, a missing `photos.js`, and no IndexedDB at all — confirming the first shows the recovery prompt and the other two still start normally.

- **Cross-session asset history + testing time (V61)** — two features that show you things already sitting in your data. **(1) Asset history.** Searching the Sessions screen has matched item asset numbers across every job since V10; what was missing was the *presentation*. A match opened its own job, so an asset tested in three jobs meant opening three jobs and reconstructing the history by hand. Now, when what you type is an asset number found in **two or more different jobs**, the search offers a consolidated view: every past test in one scrollable sheet, newest first, each showing date, job, pass/fail, location, item type, readings (when the Test Readings feature is on and that item carries them) and notes — with a tap to jump straight to the original item in its own job. The matching rule is deliberately narrow: **exact text, case-insensitive and trimmed, asset numbers only**. Not a substring, because typing `1` must not claim to be the history of asset `1024`; not zero-insensitive, because `001` and `1` stay different assets exactly as duplicate detection has treated them since V60 — if you typed the zeros, you meant them; and not the broader search that also matches locations, item types and notes, because "history for kettle" is meaningless when a kettle is a hundred different appliances. Entirely a read over existing data: no new storage, no migration, no `backupVersion` bump. **(2) Testing time.** Every job now shows how long it took under Session settings — first item logged to last, breaks included, labelled honestly as such rather than dressed up as time on tools. A job picked up again days later reports "spread across N days" instead of a misleading 26-hour elapsed figure, where N counts **days actually worked** (a job on the 10th and 12th says 2, not 3 — nothing was logged on the 11th). The span is computed **earliest-to-latest timestamp**, not first-array-element to last, which stays correct when items are edited or re-ordered, when a CSV import brings in items with no timestamp at all, and for jobs straddling this release with some items stamped and some bare. Fewer than two timestamped items means no figure, and the line is omitted entirely rather than printing a meaningless "0m". It can also print on the certificate, but it is **off until you switch it on** under Report settings → What to include — the one "show" flag in the app that defaults off, because a certificate is client-facing and how long a job took is the engineer's business before it is the customer's. **The deliberate data-layer change underneath both:** item timestamps are now captured on **every** item's first log, unconditionally. Before V61 the Item Timestamps setting gated both capture *and* display, with the code documenting an off-path guarantee that nothing was written at all — that guarantee is now knowingly gone, and the setting gates **exposure only** (the CSV Time column and the per-item line in the Overview). The reasoning: a derived figure nobody can see unless they enabled an unrelated setting years ago is not a feature, capture is cheap (`ts` is codec-mapped to a single character — roughly 30 bytes an item, ~30 KB per thousand items against a 5 MB budget), and every day capture is on is another day of history to compute from. The visible consequence, stated in the app's own changelog rather than left to surprise anyone: switching Item Timestamps on now reveals times for everything logged since V61, not only from the moment you switched it. No new files, no new storage keys, **no `backupVersion` bump** (stays 5). Validated by the full sweep: syntax check on all 21 JS files, duplicate-declaration scan, load-order verification, and a **205-assertion** stubbed-DOM smoke harness — mutation-tested four ways by deliberately re-gating timestamp capture, copying the neighbouring `!== false` default onto the certificate flag, relaxing exact asset matching to substring, and making matching zero-insensitive, each confirmed to make the harness fail before the code was restored.
- **One-tap bug report + leading zeros (V60)** — two field-driven changes plus a naming sweep. **(1) Report a problem.** Settings → Contact now carries a **Report a problem** button opening a short sheet: pick the kind of report (Bug / Idea / Feedback), and for a bug say how bad it is (three plain-language options — "the app won't work", "wrong or annoying", "small thing" — mapped internally to P1/P2/P3) and whether it happens **every time**, **just once**, or you **haven't tried**. Then describe it in your own words. Everything else the app fills in itself: app version, the **live service-worker cache name** (the most valuable line in the report, because a cache-first PWA can be serving a build several versions old while the About page happily shows the version its *cached* config claims — this exposes a stale install instantly instead of after an evening chasing a fixed bug), installed-app vs browser tab, online/offline, screen size, device/OS string, engineer name, job and item counts, storage used, feature flags, list sizes, and any runtime errors the app caught. The composed email carries a machine-sortable subject — `[PATGo BUG P1] V60 — …` — so an inbox can be triaged by type and severity without opening anything, and a fixed `KEY: value` body inside a fenced diagnostics block. **Privacy is the design constraint, not a footnote:** diagnostics are **counts and flags only** — no client names, site names, locations, asset numbers, item types or notes ever leave the phone — and the sheet shows the exact payload read-only before sending, so nothing goes unseen. Sending uses `mailto:`, deliberately *not* a network POST: the app is offline-first and engineers are usually in a plant room or basement when something breaks, i.e. exactly where an HTTP request would fail, whereas the mail client queues the message and sends it when signal returns. A **Copy instead** fallback covers a device with no mail client. **(2) Error capture.** An in-memory ring of the last three runtime errors (`window.onerror` + `unhandledrejection`) so a report carries the actual throw rather than "it went blank". **Never persisted** — it lives and dies with the page, so it cannot grow, cannot corrupt a save and cannot leak into a backup; the trade is that a crash-and-reload loses its own error text, accepted because putting the error path on the storage path is the one risk not worth taking. Known limit, stated rather than hidden: `boot.js` loads last, so a *parse-time* failure in an earlier file happens before the handlers exist — that class is already covered by the boot integrity guard, which in V60 carries its own **self-contained report link** (as does the render-failure fallback), deliberately duplicating a little code rather than depending on files that by definition may not have loaded. **(3) Leading zeros in asset numbers.** Start a job at `001` and it now continues `002`, `003` instead of jumping to `2`. The real blocker was the New Session start-number field being `type="number"`, which normalised `001` to `1` before the app ever saw it; it's now `text` + `inputmode="numeric"`. Padding is **opt-in by deliberate act** — type a plain `1` and nothing changes — and the width **never truncates** (`099` → `100`, `999` → `1000`), because wrapping or clipping would silently produce duplicate asset numbers on a real job. Mid-job hand-typed padding is followed too, and pre-V60 sessions (no `startPad`) behave exactly as before with no migration. `001` and `1` remain **different** asset numbers for duplicate detection — if you typed the zeros you meant them. **(4) Naming sweep.** The last 15 internal "PAT Test PWA" banner comments across 10 files became "PATGo PWA". Deliberately left alone: the `PAT Tester` item type and "your PAT tester" settings copy (both refer to the physical instrument), the `pat-testing-training.net` reference URLs, and — critically — the `pat:` localStorage key prefixes and the `pat-vNN` cache key, since renaming those would orphan every user's data. One new file (`bugreport.js`, 21 first-party scripts), one additive session field (`startPad`) that the storage codec passes through unmapped, and **no `backupVersion` bump** (stays 5). Validated by the full sweep: syntax check on all 22 JS files, duplicate-declaration scan across 524 symbols, load-order verification, and a **228-assertion** stubbed-DOM smoke harness — including a dedicated privacy group that seeds fake client names, sites, asset numbers, locations and notes into state and asserts none of them appear anywhere in the diagnostics or the assembled email, itself mutation-tested by deliberately introducing a leak and confirming the assertions fail.
- **Lifetime stats counter (V59)** — a running tally at the bottom of the Settings screen: how many items you've tested, how many failed and the percentage, and your most common item type. The design problem worth explaining is **pruning**. A counter computed live from the sessions currently on the phone would *fall* every time you cleared out old jobs — you'd tidy up and watch your lifetime total shrink, which reads as broken rather than fun. The obvious alternative, incrementing a stored counter each time an item is logged, is worse: it needs hooks in item save, item delete, bulk delete and CSV import, plus adjustment logic when a pass is edited into a fail, and double-counting is its failure mode. V59 uses a third shape — an **archive bucket**. The figure shown is *live* (counted from current sessions, never stored, so it can't drift from the real data) plus *archived* (a small persisted bucket). At the two — and only two — points where a session leaves the app for good, `deleteSession` and `pruneOldSessions`, that session's tallies are folded into the bucket **before** it goes. There are exactly four places the session list is reassigned (load, restore, prune, delete), so those two hooks cover every removal path with none unaccounted for. The result: clearing out old jobs no longer costs you the numbers, editing an item can't double-count, and CSV-imported sessions need no special handling because they simply appear in the live half. **Deliberate exclusions:** item-level deletes are *not* archived (that's correcting a mis-entry, not history leaving, and archiving it would let a typo permanently inflate the total), the demo/example session is excluded from both halves, and the bucket is **not** part of the Export Setup bundle — Export Setup is config-only and these are derived from job data. **Backup behaviour:** the bucket rides in the JSON backup, and restore puts it back through the same validator used on load, so restoring returns the counter to exactly what it was when the backup was taken rather than desyncing; a pre-V59 backup has no such key and correctly restores an empty bucket. Additive and missing-field-tolerant, so **no `backupVersion` bump** (stays 5). One honest limitation, stated in the app's own changelog: the counter starts from the sessions on the device at upgrade time — anything pruned *before* V59 is unrecoverable — so it becomes a true running total from this release onward. Validated by the full sweep: syntax check on all 21 JS files, duplicate-declaration scan, load-order verification of all nine new symbols, a 102-assertion stubbed-DOM smoke harness (live counting, the delete and prune hooks holding the total, demo-session exclusion in both halves, item-deletes correctly *not* archived, validator hardening against negative/fractional/NaN/Infinity/array/string input and a 200-entry type map, corrupt-storage recovery, save-through-validator, escaping, tie-break stability and zero/100% edge cases), and a 42-assertion lifecycle harness walking the real scenario end to end — log work, back up, prune everything, reload the app, restore — asserting the total never moves at any step and that restoring cannot double-count.

- **Field bug fixes — sheet scrolling & dropdown taps (V57)** — two fixes reported from field testing, both in the touch-interaction layer. **(1) The preset switcher wouldn't scroll.** Press-and-hold on the Quick Pick grid opens a bottom sheet listing every preset; the shared bottom-sheet shell had no height cap and no overflow, so once the list was taller than the screen it grew off the *top* with nothing to scroll — presets at the top of the list were simply unreachable. The shell is now capped (`85dvh`, with a `vh` fallback for older iOS) and laid out as a flex column, with a new `.sheet-scroll` region that scrolls the list while the drag handle, header and "Edit presets" footer stay pinned. The fix is on the shared shell, so it pre-empts the same latent bug in the fail, readings and Multi Pick sheets. **(2) Typed suggestions sometimes ignored a tap.** The three suggestion dropdowns (item type, location, and the New Session client/site fields) committed the pick on `click`, relying on an `onmousedown → preventDefault` trick to stop the input's blur tearing the list down first. On iOS that's a race the tap sometimes lost — blur won, the 150 ms blur timer removed the list, and the tap landed on nothing; hence the intermittent "sometimes it works, sometimes not". All three now **commit on `pointerdown`**, which fires first and reliably for touch, so the choice is captured before any blur can cancel it. **Also:** now that the preset list scrolls, a scroll-drag could have ended in a click on whichever row sat under the finger and silently switched the preset — a document-level drag guard (10 px slop, reset on every `touchstart`) makes the pick ignore any gesture that drifted, so scrolling never switches a preset while a genuine tap is unaffected. All changes are behavioural — no new storage keys and **no `backupVersion` bump** (stays 5). Validated by the full sweep (syntax check, duplicate-declaration scan, load-order check, and a 29-assertion stubbed-DOM smoke harness covering the drag guard's tap/scroll/reset behaviour, the guarded pick action, the pointerdown binding across all three dropdowns, and the sheet-scroll markup and CSS).
- **Retest reminders — commercial chase list (V56)** — a business-development tool that reminds you to contact past customers and rebook their testing, so repeat work doesn't slip. It is deliberately **not** a compliance due-date display: it's a worklist of jobs *you've chosen* to chase. Gated twice so it never becomes noise. First, a **master switch** (Settings → Retest Reminders), **off by default** — while off, nothing about the feature appears anywhere, so subcontract-only and non-commercial users never see it. Second, **per-session opt-in**: even with the feature on, a job only joins the chase list when you flag it under its Session settings ("Remind me to chase this for retest"). Lost jobs, one-offs and subcontract work are simply never flagged (or flagged then resolved), keeping the list trustworthy. Each flagged job's due date is its **test date + a retest interval** captured per-session from your Report Settings default at flag time (editable per job, so changing the global default never silently moves existing dates). Urgency bands are **Overdue / Due soon (≤60 days) / Upcoming (≤90 days)** — wider than the 30-day calibration window because winning repeat work needs lead time. When the feature is on and a flagged job is due, a **banner** appears on the Sessions screen, the session row shows a 🔔 **chip**, and a **"Retest due" filter** is offered on the Sessions list. The banner opens a dedicated **Retest reminders view** — a client/site-centric list sorted most-urgent-first, each row showing who to ring and the due date, with a one-tap action to mark the outcome: **Rebooked** (job won) or **Declined** (lost it), either of which clears it from the active list; you can also stop reminding entirely. Honest scope note: reminders surface **in-app when you open the app** — they are not scheduled phone push notifications (that's planned for the PAT Cloud service), and the in-app copy says so. **Data-model note:** the three per-session fields (`retestTrack`, `retestMonths`, `retestContact`) are additive and ride backup/restore wholesale through a defensive validator (`normaliseSessionRetest`) — **no `backupVersion` bump** (stays 5). - **PDF symbol fix + CSV polarity column (V55)** — two small fixes. On the PDF certificate, the reading-column headers and values were printing the ohms (Ω), greater-than-or-equal (≥) and tick (✓) characters as the wrong glyphs (©, an `e`, and a fallback mark), because jsPDF's built-in font uses single-byte WinAnsi encoding which has no glyph for those codepoints. Rather than ship a heavyweight Unicode font (which would bloat the offline-first precache and is awkward to maintain in a phone-editable, no-build-step repo), V55 swaps just those few characters for plain-ASCII equivalents **in the PDF layer only** — `Ohms`, `MOhms`, `>=`, and `Yes` — via a small `pdfSafe()` helper applied to the report table. The on-screen readings sheet and the CSV export keep the proper Unicode symbols (browsers and spreadsheets render them fine). Also new: an optional **Polarity column in the CSV export** for Class I items — off by default like the other reading columns (Settings → CSV Columns), printing `Yes` when a Class I item recorded a polarity tick and blank otherwise. Both changes are additive — **no `backupVersion` bump** (stays 5). Validated by the full sweep (syntax check, duplicate-declaration scan, load-order check, and a stubbed-DOM smoke harness covering the glyph swaps and the CSV polarity cell across feature-on/off, ticked, false and absent).

## Stack

Vanilla HTML / CSS / JS — no frameworks, no build step. Service-worker cached for full offline use. State lives in `localStorage` (session data is key-shortened/compressed at the storage boundary since v14; backups stay human-readable).

**Third-party code:** from V30, the app bundles two MIT-licensed libraries — **jsPDF** and **jsPDF-AutoTable** — for client-side PDF generation. They are vendored as minified UMD files (`jspdf.umd.min.js`, `jspdf.plugin.autotable.min.js`), served from the app’s own origin and service-worker **precached** so reports work fully offline. From V51 they are no longer loaded in the startup `<script>` chain — they’re **injected on demand** on the first report (from the precache), so they no longer add to cold-start cost while still being instantly available offline. From V38 the app also bundles **PDF.js** (Mozilla, Apache-2.0) for the multi-page report preview, vendored as `pdfjs.min.js` + `pdfjs.worker.min.js`; unlike the jsPDF libraries these are **not** precached — they’re fetched lazily from the app’s own origin on the first preview and then service-worker cached. See `THIRD-PARTY-LICENSES.txt`. Both MIT and Apache-2.0 permit commercial/subscription use with no royalty. (Prior to V30 the app had no external dependencies at all.)

## Files

The app logic was split out of the old single `app.js` into single-concern script files during the V21/V22 refactor. V25 added `dispatch.js` for delegated CLICK handling; V28 (E3-tail) finished the job by moving every stateful input/change handler into `dispatch.js` too, leaving only four focus-sensitive fields directly bound. V29 removed the last two no-op binder shells left over from that migration. They share one global scope and load in a fixed order (see `MAP.md` for what lives where).

**Load order (defined in `index.html`):**

`config.js` -> `state.js` -> `utils.js` -> `storage.js` -> `clients.js` -> `sqp.js` -> `multipick.js` -> `feedback.js` -> `bugreport.js` -> `csv.js` -> `backup.js` -> `session.js` -> `setup.js` -> `tour.js` -> `report.js` -> `pdfpreview.js` -> `render-core.js` -> `render-settings.js` -> `events.js` -> `dispatch.js` -> `boot.js`

(`jspdf.umd.min.js` + `jspdf.plugin.autotable.min.js` are vendored and **precached** in the service worker, but from V51 are **not** in this startup chain — `report.js` injects them on the first report. `pdfjs.min.js` + `pdfjs.worker.min.js` are vendored but **neither** in this chain nor the precache — they load lazily on first preview.)

## Deployment

GitHub Pages, auto-deploys on commit to `main`. Edit via the GitHub web UI for quick iterations — **upload file contents, not the folder.**

## Releasing

1. **Always bump `CACHE_VERSION` in `sw.js`** when any file changes (`pat-vN`; hotfix `pat-vN-1`). This is the step that must never be skipped — a stale cache serves old/broken files.
1. **Always bump `APP_VERSION` in `config.js`** for the user-visible version label.
1. If scripts are added/removed, update both the `<script>` tags in `index.html` and the `ASSETS` list in `sw.js` (keep load order; `boot.js` stays last).
1. Roll the About changelog in `render-settings.js` (most recent 3 versions). For feature releases, roll the welcome modal (new `pat:vNNwelcome` key); skip it for pure structural/refactor releases.
1. If the storage schema changes, bump `backupVersion` in `backup.js` and confirm older backups still restore.
1. Replace the changed files via the GitHub web UI and commit each.
1. Wait ~1 min for Pages to redeploy, then verify in incognito before testing the installed PWA.
1. On a phone, fully close the PWA from the app switcher and reopen once or twice to force the service-worker refresh. The app also shows an “Update available” banner when it detects a new version — tap Refresh to activate.
1. **Run the release’s post-commit test checklist** (every release ships with one in its handoff) to confirm the new features/fixes actually work on the live app — not just that the deploy landed.

### Hotfixes

A hotfix (e.g. `v25.1`, `v25.2`) bumps the cache to `pat-vNN-1` and **amends the existing handoff doc** for that version to record what changed, why, and which files were touched — so the handoff stays the accurate current-state record.
